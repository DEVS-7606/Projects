PROJECT: Invoice Management MVP for Micro-SMEs

1. PRODUCT SUMMARY

We are building a focused invoice workflow tool for micro-SMEs.
This is NOT a super app and NOT full accounting software.

Core promise:
"Forward invoice emails to the app, auto-extract invoice data, and track unpaid/overdue invoices in one dashboard."

Primary target users:
- Micro-SMEs
- Small traders
- Service businesses
- Agencies
- Businesses that receive invoices by email and currently track them manually

2. V1 GOAL

V1 should solve only these problems:
- Collect invoices from forwarded emails
- Extract invoice data from PDF/image
- Store invoices in one place
- Manage vendors
- Show invoice status
- Let user mark invoice as paid
- Show basic totals

Do NOT build in v1:
- WhatsApp integration
- Full accounting
- GST filing
- Payment gateway flow
- Team accounts
- Billing/subscription system
- Invoice line items
- OCR perfection
- Advanced analytics

3. V1 CORE USER FLOW

Step 1:
User signs up and logs in.

Step 2:
User sees a unique forwarding email, for example:
invoices+username@yourapp.com

Step 3:
User forwards supplier invoice emails to that address.

Step 4:
System receives the email and attachment.

Step 5:
System stores the file and extracts invoice details using OCR.

Step 6:
System creates an invoice record.
If extraction is unclear, mark invoice as "needs_review".

Step 7:
User opens dashboard, reviews invoice, edits fields if needed.

Step 8:
User tracks invoices by status:
- unpaid
- paid
- overdue
- needs_review

Step 9:
User marks invoice as paid manually and adds payment reference if needed.

4. V1 ENTITIES

Main entities:
- Profile
- Vendor
- Invoice

Relationship:
- One user/profile has many vendors
- One user/profile has many invoices
- One vendor can have many invoices
- An invoice may belong to one vendor
- An invoice may optionally point to another invoice as duplicate_of_invoice_id

5. V1 BUSINESS RULES

- Every vendor belongs to one user
- Every invoice belongs to one user
- Vendor should be unique per user by name
- Invoice status allowed values:
  unpaid, paid, overdue, needs_review
- Invoice source allowed values:
  email, upload, manual, whatsapp
- Duplicate status allowed values:
  none, suspected, confirmed, ignored
- Do not auto-delete duplicates
- Flag duplicates for user review

6. FRONTEND MODULES

Frontend should include:
- Auth pages
- Dashboard page
- Vendors list page
- Vendor form modal/drawer
- Invoices list page
- Invoice detail page/drawer
- Invoice review/edit form
- Basic stats cards
- Empty states
- Loading states
- Error states

7. BACKEND MODULES

Backend should include:
- Supabase auth
- profiles table
- vendors table
- invoices table
- RLS policies
- email ingestion endpoint
- file storage for invoice PDFs/images
- OCR extraction service
- duplicate detection logic
- invoice status logic

8. V1 SUCCESS METRICS

A successful v1 means:
- User can sign in
- User can forward email successfully
- Invoice appears in dashboard
- User can edit invoice
- User can mark invoice paid
- Data is safely isolated by user
- 5 to 10 beta users can use it without constant manual support

9. RECOMMENDED BUILD ORDER

Phase 1:
- Project setup
- Supabase connection
- Auth
- Basic layout

Phase 2:
- profiles table
- vendors table
- invoices table
- RLS policies

Phase 3:
- Vendor CRUD
- Invoice CRUD
- Dashboard listing and filters

Phase 4:
- Email forwarding flow
- File upload and storage
- OCR parsing
- Create invoice from parsed data

Phase 5:
- Review screen
- Duplicate flagging
- Manual mark as paid
- Basic totals

Phase 6:
- Bug fixing
- Soft beta launch
- Feedback loop

10. DESIGN PRINCIPLES

- Keep UI simple and business-focused
- Prioritize table usability over fancy visuals
- Design for speed and clarity
- Mobile support is useful, but desktop-first is acceptable for v1
- Build ugly but functional first
- Avoid overengineering

11. FUTURE FEATURES AFTER V1

Only consider later:
- WhatsApp forwarding
- Automated reminders
- Payment matching
- GST-friendly exports
- Team accounts
- Billing and paid plans
